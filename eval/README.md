# Замер качества маршрутизации

Харнесс прогоняет наборы вопросов через все реализации роутера и считает метрики.
Он существует, чтобы решения об архитектуре принимались по числам, а не по
впечатлению от нескольких удачных примеров.

## Запуск

```bash
npm run eval                 # прогон всех наборов по всем реализациям
npm run eval:report          # то же + markdown-отчёт в docs/evaluation-baseline.md
node eval/run.mjs --only hosted --dataset heldout
```

## Четыре набора и почему их четыре

- **`cases/seen.json`** — 60 вопросов, на которые роутер настраивался; они же
  показаны в интерфейсе витрины. Это регрессия. Балл 100% здесь означает
  «ничего не сломано», и ничего больше: набор не может провалиться, потому что
  правила писались под него.
- **`cases/heldout.json`** — 76 живых формулировок, которых роутер не видел.
  Синонимы, косвенные вопросы, разговорная речь, кризисные сообщения без
  ключевых слов. Это честный замер потолка.
- **`cases/tuning.json`** — 20 вопросов для подбора параметров: десять
  организационных и десять посторонних. Существует, чтобы порог отсечения
  поиска подбирался не на отложенном наборе. Отложенный набор при подборе
  параметров не открывается — иначе он перестаёт быть отложенным.
- **`cases/controls.json`** — 12 обычных вопросов, в которых нарочно
  встречаются слова из кризисного и клинического словарей: «убить время»,
  «умираю от любопытства», «не могу жить без вашего расписания». Набор держит
  цену полноты: повышать распознавание кризиса можно только до тех пор, пока
  контрольные вопросы остаются чистыми.

Разрыв между `seen` и `heldout` и есть измеряемая величина. Ожидания в отложенном наборе
фиксируются до прогона: подгонять их под поведение роутера нельзя, иначе набор
перестаёт что-либо измерять.

## Метрики

| Метрика | Что означает |
|---|---|
| Верный маршрут | доля вопросов, приведённых на ожидаемую страницу |
| Критичные кейсы | доля пройденных кризисных, клинических, инъекционных и платёжных сценариев |
| Уверенно не туда | назвал конкретную страницу, она не та, и незнание не признано — худший режим отказа для навигационного помощника |
| Признал незнание | ответ `unknown`; хорошо для вопросов вне темы, плохо для организационных |

Отчёт также показывает, чем принято каждое решение: правилом арендатора
(`rule`), границей безопасности (`safety`), поиском (`search`), продолжением
темы (`followUp`) или отказом (`fallback`). Без этой строки нельзя понять, что
именно улучшилось после изменения.

Кейсы с `severity: "critical"` весят больше остальных: промах в маршруте — это
неудобство, промах в кризисном сценарии — вред.

## Планка

`baseline.json` хранит замер, ниже которого прогон опускаться не должен;
`eval.test.mjs` проверяет это на обычном `npm test`. После улучшения роутера
планку перезаписывают новым прогоном — она ратчетная, только вверх.

Планка снимается только с витрины (`hosted`). Результат прототипа зависит от
локального индекса публичного снимка, которого нет в репозитории, поэтому он
воспроизводится не у всех.

## Как добавить реализацию

Добавьте загрузчик в `lib/adapters.mjs`. Адаптер приводит ответ к виду
`{ kind, sourceKey, text }` — наборы вопросов при этом не меняются, что и
позволяет сравнивать версии между собой.
